# 上下文控制设计：三层机制（L0 / L1 / L2）

> AI Model Router 的上下文控制设计文档。先研究五家厂商 coding agent 的机制，再综合出一套适用于"无状态转发层"的分层方案。

## 1. 背景：上下文控制在解决什么问题

模型有上下文窗口上限（200K～1M token）。一次深度任务中，读文件、跑命令的产出动辄数千 token，几十上百轮交互后轻松突破上限——超了就报错或"失忆"。

各家 agent 的解法不是"一刀切截断旧消息"，而是**分层防线 + 摘要替身 + 关键内容永不清除**：

1. 先处理最占空间的（超大工具输出）
2. 再删/叠最没用价值的（完成使命的早期消息）
3. 最后才整体压缩（LLM 把历史写成一篇结构化摘要）
4. 摘要只替代"过程"，**用户意图、持久规则、最近几轮原文**始终保留

## 2. 厂商机制调研总览（2026-09-11 调研）

| 维 度 | Claude Code | OpenAI Codex | Gemini CLI（开源） | DeepSeek | GLM |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 机制 | 四层渐进：工具结果预算 → Snip → Microcompact → Auto Compact | 服务端"加密摘要块"（Memento） | 阈值触发 + 结构化快照 + 保留尾窗 | 模型侧压缩注意力 + 磁盘缓存 | 复用 Claude Code 机制 |
| 触发时机 | 接近上限自动；`/compact` 手动 | 90% 上下文 | 默认 50% 用量（可配） | -（1M 窗口内不裁） | Claude Code 同款 + 窗口调 1M |
| 摘要谁来做 | Claude 模型 | 服务器上经训练的小模型 | Gemini（两次调用 + 自查） | -（模型自带压缩注意力） | Claude 体系 |
| 保留什么 | system/CLAUDE.md/计划 + 最近 5 个文件 | 用户消息逐字保留（64K 预算）+ 指令重注入 | 环境上下文 + 快照 + 最近 30% 原文 | 全量（1M 内不裁） | 同 Claude |
| 亮点 | 粒度最细、四层中最成熟 | 用户意图永不被改写 | 快照结构最工程化、防注入 | 缓存 20 倍价差驱动成本设计 | 1M 兜底 + 生态兼容 |

### 提炼出的五条共同规律

| # | 规律 | 含义 |
| :-: | :--- | :--- |
| 1 | 分层防线，先轻后重 | 先清"最大块"（工具输出），再裁"死消息"（完成使命的早期轮次），最后才整体摘要 |
| 2 | 摘要只替身、重载靠源头 | 持久规则（CLAUDE.md/system）不参与摘要；最近一轮或尾窗原文永远保留；**最后一条用户意图消息永不改写** |
| 3 | 摘要质量靠结构 | "继任者便条"模板（目标/约束/关键知识/产物轨迹/当前状态/下一步）大幅降低信息丢失；防注入指令是标配 |
| 4 | 失败要有退路 | 压缩后校验确实变小；出现抖动就放弃并降级，不无限循环 |
| 5 | 顺序即成本 | 稳定前缀前置、易变后缀置尾，缓存命中率直接决定价格（DeepSeek 特有） |

## 3. Router 三层方案

前提校准：Router 是**无状态的转发层**，只整形"单次请求的 messages 数组"，不负责跨会话记忆（那属于客户端职责）。因此不做会话级摘要缓存，聚焦单请求静态整形，避免过度设计。

### 3.1 分层结构

| 层 | 职责 | 触发 | 借鉴来源 |
| :--- | :--- | :--- | :--- |
| L0 工具结果预算 | 超大 tool 结果截断为"前 N 字符 + 截断说明" | 无条件，与策略无关 | Claude Code L1 / Gemini truncateHistoryToBudget |
| L1 智能截断 | 保留 system + 最近 N 轮原文，中间旧轮次丢弃（补省略提示）；仍超则从尾窗继续裁 | 粗估 token > maxTokens | Gemini Extract+Tail / Codex 用户消息逐字保留 |
| L2 快照摘要 | 旧消息交便宜模型蒸馏为 `<state_snapshot>`（6 段 XML），拼 system + 快照 + 尾窗 | summarize 策略且粗估超阈值 | Gemini state_snapshot / Claude Auto Compact |

### 3.2 策略参数（Rule → then.context）

| 字段 | 类型 | 默认 | 说明 |
| :--- | :--- | :--- | :--- |
| strategy | enum | none | none=原样；truncate=L1；summarize=L2（失败自动降级 L1） |
| maxTokens | number | 60000 | 触发阈值（估算 = 消息 JSON 字符数 / 4） |
| tailRounds | number | 2 | 保留最近 N 轮原文 |
| maxToolChars | number | 4000 | L0 工具结果预算（字符） |
| summarizeModel | string | deepseek-flash | L2 摘要模型（便宜模型） |

### 3.3 执行流程

```
请求进入
 1. L0：无条件截断超大 tool 结果（> maxToolChars → 前 N 字符 + 说明）
 2. 粗估 token ≤ maxTokens？ → 原样发送（仅 L0 可能生效）
 3. L1 truncate：保留 system + 最近 tailRounds 轮原文
      丢弃旧轮次（补一行"此前 N 轮历史已省略"）
      仍超 → 从尾窗继续裁；再超 → 内容级截断（单条消息按分摊预算保头部）
 4. L2 summarize：可压缩历史（tailRounds 之外）交摘要模型
      v 输出 <state_snapshot>（整体目标/约束/关键知识/产物轨迹/最近动作/当前状态）
      v 校验 token 确实变小
      v 失败（≥400/无令牌/解析失败/膨胀）→ 降级 L1
 5. 拼装发送：system +（快照 | 尾窗原文）+ 省略提示
```

### 3.4 降级链与防抖

| 场景 | 处理 |
| :--- | :--- |
| L2 摘要调用失败 | 降级 L1，不阻断转发 |
| 摘要后 token 未变小（inflated） | 判定失败，降级 L1 |
| 单条消息自身超预算（一次性粘贴 100K+ token 长文） | 轮次裁剪无效 → 内容级截断：按消息分摊预算，保留头部 + 截断说明 |
| 摘要输入预算 | 可压缩历史 JSON 截前 48K 字符喂摘要模型，控制摘要调用自身成本 |

### 3.5 可观测性

- 响应头 `x-context-action`：none / tools / truncate / summarize，客户端可感知是否被处理。
- 请求日志 `context_action` 列落库；摘要自调用独立记账（route_source=summarize），真实 usage 与成本入总账，不污染业务统计。

## 4. 实测验证（2026-09-11）

| 用例 | 输入 | 结果 |
| :--- | :--- | :--- |
| L1 truncate | 450K 字符单条消息 + 4 条消息 | 200，ctx=truncate，上游实收 16.7K token（450K → 16718） |
| L2 summarize | 10 轮历史 ≈ 316K 字符 | 200，ctx=summarize，多轮历史压缩进 state_snapshot |
| L0 tools | 3000 行 JSON 工具结果 | 200，ctx=tools，工具消息被裁至 4000 字符 |

实测中还发现并修复了一个缺陷：单条消息自身超过预算时，轮次裁剪无法缩小载荷（最后一条 user 永不截断是原则，但内容极度过长时没有兜底），会导致上游预扣费失败。修复为内容级分摊预算截断。

## 6. 已知边界与路线图

| 项 | 现状 | 未来方向 |
| :--- | :--- | :--- |
| 摘要范围 | 仅覆盖可压缩历史前 48K 字符 | 扩大预算或按主题分块摘要 |
| 摘要质量 | 单遍生成 | Gemini 式"两遍自查"（第一遍生成，第二遍查漏） |
| 会话缓存 | Router 无状态，不做 | 由客户端/上游承担 |
| 主题级压缩 | 一次性全量压缩 | union-find 聚类成"剧集"，增量后台压缩、LRU 逐出留墓碑 |
| 缓存命中优化 | 固定 system 前缀 + 稳定消息顺序 | 统计缓存命中率并指导 prompt 布局 |
